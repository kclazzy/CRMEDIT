Каждая запись: что сделано и почему.

## 15.11.2026 — этап 1, ядро

1. **Репозиторий оказался пустым** → работа ведётся сразу в `main`, первой фиксацией.
2. **Написано ТЗ (`docs/TZ.md`) до кода.** Причина: исходный запрос содержал неизмеримые и неоднозначные условия; 11 правок зафиксированы в разделе 2, чтобы код строился от согласуемого документа.
3. **Рабочее пространство Cargo с отдельным `crm-core`.** Причина: модель описания нужна и редактору, и будущему исполнителю, и установщику — одно определение в одном месте.
4. **Модель описания CRM (`Definition`) — через тесты.** Сначала написаны 19 тестов поведения, получен ожидаемый отказ сборки (нет типов), затем реализация. Все правила корректности собраны в одной функции `check`; любое изменение применяется к копии и проверяется целиком, чтение из JSON идёт через ту же проверку. Причина: некорректное описание должно быть невозможно построить (ТЗ, К-5).
5. **Удаление заменено скрытием.** Причина: правка 7 ТЗ — у клиента уже могут быть данные; откат ошибочного добавления даёт история.
6. **Отказ от файла-признака проекта** (правка в П-1). Причина: «проект существует ⇔ существует снимок № 1» делает создание атомарным и убирает состояние «признак есть, истории нет».
7. **Проект в папке (`Project`) и реестр (`Registry`).** Тесты (18 + 5) написаны до реализации. Запись снимка — «временный файл + жёсткая ссылка»: файловая система сама отказывает второму писателю, блокировок и общего состояния нет (ТЗ, П-5). Номер снимка хранится только в имени файла, активный проект — только как первый элемент реестра: по одному месту на каждое решение. Время передаётся параметром, чтобы логика оставалась проверяемой без часов.
8. **Редактор `crmedit` (командная строка).** 13 сценарных тестов написаны первыми и вызывают редактор так же, как пользователь: строка команды → текст и файлы. Причина выбора командной строки для этапа 1: она даёт проверяемый сквозной сценарий раньше, чем появится окно, а окно (этап 3) будет вызывать те же операции ядра. Часы, рабочая папка и расположение реестра передаются через `Env` — тесты не зависят от машины.
9. **Проверено вручную на собранной программе:** создать → добавить сущность и поле → история → возврат → второй проект → список проектов → ошибка с плохим идентификатором (код возврата 1).
10. **CI (`.github/workflows/ci.yml`).** Причина: целевая платформа — Windows, а разработка шла на Linux; тесты и сборка `crmedit.exe` на Windows должны выполняться при каждом изменении (ТЗ, Н-6).
11. **Мутационное тестирование (`cargo mutants`).** Первый прогон: 238 мутантов, 11 выжили. Действия: добавлены тесты (флажки в JSON, текст ошибки идентификатора, нечитаемый реестр, удалённый проект, даты на границах столетий, запуск самой программы с проверкой кода возврата); из `Project::seqs` убрана отдельная ветка «папки нет» — она дублировала общую обработку ошибок. Второй прогон: 235 мутантов, выжил 1.
12. **Оставшийся мутант — осознанно.** `store.rs`, `write_new`: «любую ошибку жёсткой ссылки считать занятым именем». Честно воспроизвести другую ошибку ссылки переносимым тестом нельзя, а плохой тест хуже отсутствующего.
13. **Инструменты `crapper` и `dryer` в окружении не найдены** — оценка сложности и дублирования выполнена чтением: функции короткие, без вложенных ветвлений; повторов логики нет (проверки — в `check`, запись — в `store`, разбор аргументов — в `args`).
14. **Не сделано в этом заходе (и почему).** Окно редактора, исполнитель и установочник — этапы 2–4: их нельзя честно проверить без Windows с экраном, а без ядра их не на чем строить. Сборка под Windows на этой машине не запускалась — её выполняет CI.

## 15.11.2026 — этапы 2–5

15. **База рабочей CRM (`crm-runtime`: `value`, `schema`, `db`).** 27 тестов первыми. Перенос данных планируется по фактической схеме базы, а не по «номеру версии» — поэтому он идемпотентен без отдельного учёта. Перед изменением — копия базы; несовместимая смена вида поля отклоняется целиком. Причина: потеря данных клиента — главный риск продукта (правка 7 ТЗ). Обязательность полей проверяется в одном месте (`parse`), а не в базе: иначе добавить обязательное поле к существующим записям было бы нельзя.
16. **Тесты нашли ошибку в разборе даты** (ISO-форма отвергалась) до первого запуска — исправлено.
17. **Действия пользователя CRM без окна (`Crm`): поиск, ссылки по названию, доска, CSV.** 16 тестов первыми. Причина: окно должно только рисовать; логика, проверяемая без окна, проверяется быстро и полностью.
18. **Окно CRM (`CrmApp`) и тесты окна через дерево доступности.** Тесты нажимают кнопки, вводят текст, выбирают из списков и сверяют и экран, и базу. Они же нашли знаки («→», «✖»), которых нет во встроенном шрифте, — заменены текстом. Диалоги выбора файлов вынесены за интерфейс `Files`, чтобы кнопки CSV тоже проверялись.
19. **Окно отрисовано без экрана и просмотрено глазами** (таблица, форма, доска). Причина: тест через дерево доступности не видит вёрстку.
20. **В ядро добавлены переименование, порядок, обязательность; подбор технического имени по русскому названию; `app_id`.** Причина `app_id`: установленной CRM нужна неизменная личность, иначе обновление не найдёт данные. Он вычисляется из неизменяемого первого снимка, а не хранится — расходиться нечему. Закреплённое в тесте значение сверено независимой реализацией хэша на Python.
21. **Одна программа — три роли (редактор, установщик, CRM).** Решение принято вместо трёх отдельных программ: сборка установочника сводится к дописыванию описания в конец собственного файла редактора, не нужны ни заготовки, ни упаковщики, и работает одинаково на любой ОС. Плата — размер установочника. Комплект защищён контрольной суммой; идентификатор CRM в нём имеет тип `Ident`, поэтому подделанный комплект не может вывести установку за пределы её папки.
22. **Установка (`setup`).** Файлы копирует программа; ярлыки и запись в «Программы и компоненты» создаёт сценарий PowerShell (есть в каждой Windows 10/11; не нужен ни `unsafe`, ни сторонние библиотеки). Исполнитель сценариев — за интерфейсом `Shell`: логика проверяется везде, настоящий PowerShell — в CI. Удаление запускает сценарий отдельно: программа не может стереть себя, пока работает.
23. **Окно редактора (`EditorApp`).** 15 тестов первыми. Они нашли два дефекта до первого ручного запуска: неоднозначную кнопку «Скрыть» и то, что выделение не следовало за перемещённым разделом. Командная строка и окно сохраняют правки одним общим путём (`save_edit`). Конфликт с другим окном не затирает чужую правку: окно сообщает о нём и показывает актуальную версию.
24. **Настоящие программы запущены на виртуальном экране** (редактор; собранная CRM). Снимок экрана показал сжатые до двух букв поля названий в таблице полей — исправлено и проверено повторным снимком.
25. **Сквозная проверка на Windows (`ci/windows-e2e.ps1`).** Сборка → тихая установка → файлы, реестр, ярлыки → запуск CRM → обновление с новым полем (ровно одна резервная копия) → удаление с сохранением данных → удаление с данными. Первый прогон упал на моей ошибке в самом сценарии (имя функции совпало со встроенным псевдонимом PowerShell).
